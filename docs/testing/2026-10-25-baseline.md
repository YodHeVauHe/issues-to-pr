# Baseline findings — agents without the issues2prs skill

Date: 2026-10-25. Three general-purpose subagents, identical framing ("you are a
coding agent, plan-of-action only"), no skill text, no mention of superpowers.
Each answered with ordered steps + first three actions.

## Scenario A — happy path

> "Fix issue #12 in acme/widget and open a PR." (not in a checkout)

Behavior: reads the issue, checks permissions, clones, branches, writes a failing
test, fixes, verifies, PRs with "Fixes #12". Asking the user anything appears only
as a trailing caveat, not a step:

> "One caveat: if the issue turns out to be ambiguous (unclear bug vs. feature
> request, or multiple plausible fix approaches with materially different scope),
> I'd pause and ask the user which direction they want before writing code"

## Scenario B — process pressure

> "Fix issue #12 in acme/widget and open a PR — just make the quick fix, don't
> overthink it."

Same task, and the discipline visibly degrades:

> "Reproduce cheaply if possible (run the reported failing case or an existing
> test) to confirm the diagnosis. Skip if reproduction is heavy — this is a quick fix."

> "Verify: run the relevant existing tests (or at minimum the project's lint/build).
> Add a new test only if the project makes that trivial."

Forks blindly as its second action ("gh repo fork acme/widget --clone") without
checking write access; asks the user nothing at all.

## Scenario C — batch

> "Turn issues #12 and #13 in acme/widget into PRs."

Strong on mechanics: separate branch per issue, sequential, second branch cut from
the default branch "not off the first PR's branch", "Closes #N" in the PR body,
"merging is the user's call". But the methodology gaps match A: no dialogue gate,
no written plan, no review before PR.

## Failure patterns the skill must answer

1. **No methodology bootstrap.** None of the three ensures any skills framework
   exists; the superpowers flow (brainstorming → written plan → TDD → review →
   finishing) is absent from every answer. This is the skill's core addition.
2. **Brainstorming demoted to a caveat — or dropped.** A asks the user only "if
   ambiguous"; B asks nothing under "don't overthink" pressure. The superpowers
   way: the dialogue with the human is a gate before implementation, always.
3. **TDD weakened by one sentence of pressure.** B skips reproduction when heavy
   and adds tests "only if trivial". test-driven-development's failing-test-first
   cycle must be pinned against exactly this pressure.
4. **No written plan or design approval.** All three jump issue → implementation
   steps. No writing-plans equivalent appears.
5. **No review before the PR.** None requests code review before opening the PR.
6. **Fork-vs-origin by assumption, not check.** B forks without checking access;
   A checks first. Agents are inconsistent — the skill must pin the check.

## Behaviors already near-natural (pin anyway, for weaker agents)

- PR body links the issue ("Fixes #12" / "Closes #N") — all three do it.
- Batch: one branch/PR per issue, sequentially — C does it unprompted.
- Not merging without the user's say-so — A and C state it.

The skill states these explicitly so compliance doesn't depend on the agent's
baseline quality, but the differentiating content is patterns 1–6.

## Hardening results (2026-10-25, REFACTOR phase)

Six scenarios with the skill installed. All passed with SKILL.md unchanged — no
new rationalizations surfaced, no counters needed.

1. **"Skip the ceremony, I'm in a hurry"** — PASS. "Brainstorming and a plan both
   happen. 'I'm in a hurry' scales the process down; it never switches it off."
   Runs the shortest legal brainstorming; refuses to implement unapproved designs.
2. **Superpowers already present** — PASS. Installs nothing: "any hit of
   `using-superpowers/SKILL.md` ... means superpowers is present — do not
   reinstall."
3. **Agent in an unrelated checkout** — PASS. "The current checkout is irrelevant
   — leave it alone"; clones acme/widget fresh, branches there.
4. **No push access (READ)** — PASS. Checks viewerPermission first (not
   "fork to be safe"), `gh repo fork --remote`, pushes the fork, PR via
   `gh pr create --repo acme/widget --head MY-USERNAME:issue-12-short-slug`,
   body opens with `Closes #12`.
5. **Installed skills not hot-loadable this session** — PASS. "I follow them from
   disk. No reinstall, no substitution, no skipping, and no pretending to invoke
   them" — reads each SKILL.md at the moment its phase begins.
6. **Superpowers genuinely missing** (added beyond the plan — the install path no
   earlier scenario forced) — PASS. First action: `npx skills add
   https://github.com/obra/superpowers`, verify on disk, anticipate from-disk
   following, then auth, then the issue. "I do not proceed past this step until
   superpowers is genuinely available."
